# Rebuild roadmap

The original app (now in `legacy/`) was rebuilt from scratch on Laravel.
Work ships one PR at a time: open the PR, the owner tests it locally, merges,
and the item is ticked off here.

## Decisions so far

| Topic | Decision |
|---|---|
| Stack | Laravel 12, PHP 8.3, MySQL 8. No framework-free rewrite. |
| Hosting | DreamHost shared, in NACOS's own account (Web Hosting Launch: 25 GB, cron, SSH; email paid after the first 3 months) rather than one shared with another person, so no one outside NACOS can read student data, the settings or votes; PHP 8.3, SSH enabled. No Redis or long-running processes; database-backed session, cache and queue. |
| Cron | `schedule:run` every minute as the site's SSH user, which also drains the job queue. DreamHost's panel can't schedule every minute (10 minutes at most), so it's set with `crontab -e` over SSH (docs/deployment.md). |
| Launch state | Not launched yet. No live data to migrate; the legacy app does not need patching. |
| Password reset | Both: email reset links (collect email at signup or next login) and one-time codes issued by an admin or course rep as a fallback. |
| Election results | Public and live during voting, for transparency. Serve a small static `live.json` snapshot rebuilt at most every few seconds; clients poll it with conditional requests (ETag/304), pause when the tab is hidden, and add jitter. No WebSockets/SSE on shared hosting. Leave a hook to switch to Pusher/Ably later. Show totals and turnout only. The snapshot is rewritten after every ballot so voters see their vote counted (the owner chose this over releasing totals in batches). |
| Late accounts | Only accounts that existed when voting opened can vote, so a candidate can't sign up unregistered classmates from the roll (by hand or by script) and vote as them. Admins can allow accounts created during voting per election ("Accounts created during voting can vote too"); for big elections, create accounts from the roll beforehand so every matric number is taken. Decided with the owner. |
| Election eligibility | Per election: limited by default to students on the nominal roll (the official list of current students an admin imports), and optionally to some levels and a range of matric entry years. The roll's level beats the one chosen at signup. Only admins create and run elections (governors are often candidates). |
| Nominal roll | Kept class by class (programme and level). Governors fill a template (class at the top, then matric number, name, email); the admin uploads each class's list as Excel or CSV, replacing that class only. Classes can also be added to (a file of extra students, or one student at a time), and single students removed. The roll is locked while voting is open in an election limited to it. Accounts are created from the roll with random first passwords on printable slips. |
| Account invitations | Accounts made from the roll can be emailed instead of printed: students with an email on the roll get a one-time link (7 days) to choose their own password, so nobody else ever sees it; the rest get slips. Sent from a button per class (never on upload, so a typo on a list doesn't reach a stranger), about 80 an hour to stay under DreamHost's ~100 emails an hour. If a student signs up and their roll row has an email, the link to finish goes to that address, not the one typed, so someone using a classmate's matric number gets nowhere. Decided with the owner. |
| Ballot secrecy | Who voted (`election_voters`) and what was voted (`election_votes`, random UUIDv4 ids, no timestamps) are stored separately. One ballot per election covering every position; skipping a position is allowed. |
| Design | Keep the original green/yellow identity, improved: design tokens, dark mode, self-hosted subset fonts and icons, cheap GPU-friendly animations that respect reduced motion. |
| Matric numbers | `F/ND/24/1234567`: programme letter, ND/HND (HD), two-digit entry year, exactly 7 digits. A year that hasn't started, or one more than 10 years ago, is refused. The older `ND/2019/CS/1234` format is no longer accepted. |
| Display name | Optional at signup and in the profile (30 characters, letters). Greetings use it; official places (roll, slips, audit log, watermark, admin pages) keep the full name. |
| Courses (arms) | HND computing is split into arms read from the matric number's 4th digit of 7: `…/321`**`1`**`…` Software and Web Development (SWD), `…/321`**`2`**`…` Networking and Cloud Computing (NCC). ND has no arms yet. Built so arms can be added later (AI and cybersecurity are rumoured) and ND could get them too. Each arm is its own class with its own nominal roll and governor. |
| Programme lengths | Full-time ND and HND: 2 years. Part-time ND and HND: 3 years. CODFEL: ND only, 2 years (could change). |
| Graduates | Keep read-only library access; can't vote or upload. |
| Governors | Each is tied to exactly one class (level, programme and arm). They review uploads for their own level only; admins review every level. |
| Exam timetable | Hidden from students until an admin shows it (Exam timetable → Show to students), so a draft or last session's isn't mistaken for the real one. |
| Programme calendars | Full-time, part-time and CODFEL keep separate calendars: each has its own academic session, its own exam timetable (shown or hidden on its own) and starts its new session on its own. |
| Operations | Deployed by a GitHub Action after CI passes on main (releases switched by a link, the last 3 kept, one-click rollback); nightly database dumps and hourly copies of new uploads to Backblaze B2 (any S3-compatible storage works), 7 daily, 4 weekly and 6 monthly dumps kept; errors, failed backups and low disk space emailed to the admin (throttled), not a third-party service; UptimeRobot watches `/up`, `/up/scheduler` and `/up/backups`. Decided with the owner. |
| Repository | Work happens in the fork `Leommm-byte/nacos-digital-library`. When everything is done, one PR goes from the fork back to `Tech-Reni/nacos-digital-library`. |

It's refused while voting is open, and can be undone until the first new roll is uploaded (students an admin moved since keep their new class). Admins can make a graduate a current student again by saving their class.
- [x] **14.6 E. Programme calendars.** Each programme has its own session (settings, dashboard) and its own exam timetable: papers belong to one programme (limited within it by levels and courses), admins switch programmes on the exam manager, and each programme's timetable is shown or hidden on its own; students see only theirs. New session runs per programme: only its students move up or graduate, only its roll is cleared and its timetables archived, and undo is per programme. An election open to the programme holds up its new session; one for another programme doesn't.
- [x] **14.6 F. UI fixes.** Long file names no longer push pages sideways on phones (fieldsets and page grids no longer grow to fit a file name); every file field shows the chosen file's name shortened to fit, its size, a thumbnail for a photo and a remove button (`<x-file-input>`), the chosen PDF on the upload form can be removed, and a newly chosen candidate photo can be taken back. Roll classes show the course in full ("HND1 SWD · Software and Web Development"), one per row on phones, with labelled Template and Upload buttons under the name.
- [x] **14.6 G. Live results.** The election page, the admin's live standings and the turnout on each card in the elections list update themselves: every 5 seconds while votes come in (a vote shows within a few seconds), slowing step by step to 30 seconds while nothing changes and fast again on the next vote; paused while the tab is hidden or the phone is offline and checked at once on return; one request per file however many places show it; slower when the phone asks to save data; longer waits after errors. Changed numbers fade in. The results file is no longer gzipped, so Apache's ETag matches and an unchanged check is a 304 (it had been downloading the whole file each time). Candidate photos in the shared file are paths, so they load at whatever address the page was opened (www or not, a LAN address in development). Decided with the owner: no WebSockets on shared hosting (no long-running processes; hosted push services cap free plans and would need a third-party host in the CSP); Reverb is the upgrade on a VPS.
- [x] **14.6 H. Announcements are for everyone or for one exact class (programme, level and course): a class's governor posts to and manages that class's (including a previous governor's), seen by the class and admins; admins post to everyone or any class and see all. Graduates see only everyone's. Drafts and scheduled ones can be previewed by those who manage them. The editor has a formatting toolbar and messages can be up to 20,000 characters.
- [x] **14.6 I. Executives and results.** "Know your executives" (public, linked from Elections): admins add each executive with position, an optional line (class or contact) and a photo, order them, or fill the list from a closed election's winners (ties are left for the admin, photos come along). Election results show each position in its own card, like the ballot.

Invitations and home.** Admin → Create accounts has "Create accounts and email invitations": students with an email on the roll get a one-time link (7 days) to choose their password and are signed in; the rest get slips. The scheduler sends them within the hourly limit (`MAIL_INVITATIONS_PER_HOUR`, default 80), sign-ups and re-sends first. Admin → Create accounts → Invitations lists the unused ones (waiting, sent, expired) with one-click re-send, a corrected address, or every expired one at once; "Forgot password" sends an unused invitation again, and signing in any other way uses it up. A "Your executives" card on the home page (students and guests) shows the first photos and links to the page.

## Why the legacy app was slow (avoid repeating these)

- The reader downloaded whole PDFs before page 1 (no HTTP Range support).
- `ALTER TABLE` / `CREATE TABLE` ran on ordinary page requests.
- Around 14 sequential queries on the dashboard, `ORDER BY RAND()`, no paging,
  unindexable `LIKE '%…%'` search.
- Render-blocking Google Fonts and a CDN icon font on every page; hundreds of
  lines of inline, uncacheable CSS per page.
- A 416 KB PNG logo used as favicon and cover placeholder; no lazy loading.
- Election results polled every 3 s per student, each poll running several
  queries plus an `UPDATE`.
- PHP session locking serialised concurrent AJAX requests.
- Heavy `backdrop-filter` blur and shadows on mobile.
